# 금융교육 PDF → 벡터 지식베이스 구축 보고

**작성일** 2026-08-14 · **대상 시스템** `edu-rag-indexer` · **DB** PostgreSQL 16 + pgvector 0.8.0 (`trading_gym_rag`)

---

## 1. 한 줄 요약

공신력 있는 금융교육 자료 **PDF 3종(1,367쪽)** 을 기계가 검색할 수 있는 형태로 가공해
**2,381개 청크 + 각 청크의 1024차원 임베딩 벡터**를 PostgreSQL에 적재했다.
이제 "금융사기를 예방하는 방법"처럼 자연어로 물으면 **금감원·예보 자료의 몇 쪽이 근거인지**를 찾아온다.

| 항목 | 값 |
|---|---|
| 원본 | PDF 3종, 1,367쪽, 152MB |
| 추출 텍스트 | 1,265,118자 → 정제 후 1,194,824자 |
| 청크 | 2,381개 (평균 641자) |
| 임베딩 | BAAI/bge-m3, 1024차원, 2,381개 전량 |
| DB 적재 | `edu_documents` 3행 / `edu_chunks` 2,381행 (50MB) |
| 처리 시간 | 8분 34초 (파싱+임베딩+적재, CPU) |

---

## 2. 왜 이 작업이 필요한가

트레이딩 짐의 **맞춤 학습 모듈(PT)** 과 **AI 트레이너 해설**은 "금융감독원 자료에 이렇게 나와 있다"고
근거를 대야 신뢰를 얻는다. 그러려면 LLM이 참조할 지식베이스가 있어야 하는데, PDF는 그대로는 검색이 안 된다.

- PDF는 사람이 읽는 **레이아웃** 형식이라 기계가 "이 문단이 무슨 내용인지" 모른다.
- 키워드 검색은 표현이 다르면 못 찾는다 ("빚내서 투자" vs "레버리지").

그래서 **의미로 검색**할 수 있게 텍스트를 잘라 **숫자 벡터(임베딩)** 로 바꿔 저장한다.
질문도 같은 방식으로 벡터로 바꾸면, 벡터끼리의 거리로 "의미가 가까운 대목"을 찾을 수 있다.

|---|---|---|---|---|
| 대학생을 위한 실용금융 (제4판) | 금융감독원 | 562 | 대학생 | 957 |
| 대학생을 위한 금융 첫걸음 | 예금보험공사 | 434 | 대학생 | 718 |

**CSV에 없는 PDF는 인덱싱하지 않는다** — 출처를 모르는 자료가 지식베이스에 섞이면

## 4. 전체 흐름

```
 data/raw/*.pdf ─┐
                 ├─▶ [1] 파싱 ──▶ [2] 정제 ──▶ [3] 청킹 ──▶ [4] 임베딩 ──▶ [5] 적재
 sources.csv ────┘   페이지별      머리글·목차     800자        1024차원        PostgreSQL
                     텍스트 추출    제거·품질판정    단위 분할     벡터 변환      + pgvector
                     (PyMuPDF)                                  (bge-m3)
```

각 단계를 **금감원 실용금융 134쪽**(레버리지 설명)이 실제로 어떻게 변해가는지로 설명한다.

### [1] 파싱 — PDF에서 글자를 꺼낸다

PyMuPDF로 **페이지 단위**로 텍스트를 추출한다. 페이지 번호를 끝까지 들고 가는 게 핵심이다.
검색 결과에 "금감원 실용금융 134쪽"이라고 근거를 표시하려면 이 정보가 필요하다.

```
134쪽 추출 결과 (1,114자, 앞부분):
"114  대학생을 위한 실용금융
매입한 뒤 주가가 20% 상승한 12,000원에 매도하였다면, 거래비용은 무시할 경우 자기자
본 100만원에 대한 투자수익률은 주가변동률과 같은 20%가 될 것이다. 그러나 투자자금
100만원 중에서 60%인 60만원은 대출자금을 사용하였고..."
```

PDF는 줄 끝에서 강제로 개행되므로 문장이 여러 줄로 쪼개져 나온다.

### [2] 정제 — 본문이 아닌 것을 걷어낸다

세 가지를 처리한다.

**(a) 머리글·바닥글 제거** — 모든 페이지에 반복되는 짧은 줄(책 제목, 페이지 번호)은 본문이 아니다.
페이지 번호만 다른 경우를 같은 것으로 묶기 위해 숫자를 `#`로 바꿔 비교한다.
(예: "113 대학생을 위한 실용금융", "115 대학생을 위한 실용금융" → 같은 줄로 인식)

**(b) 목차 페이지 제거** — 목차는 "제목 ⋯⋯⋯ 436" 형태라 본문처럼 보이지만 내용이 없다.
그대로 두면 검색 결과 1위로 목차 조각이 올라오는 일이 생긴다(실제로 겪었고 6절 참조).

**(c) 품질 판정** — 인덱싱하면 안 되는 파일을 걸러낸다.
- 페이지당 평균 50자 미만 → **스캔본**으로 판정, `NEEDS_OCR`로 분류만 하고 제외 (OCR은 범위 밖)
- `(cid:123)`·`�` 비율이 높음 → **폰트 깨짐**으로 판정, 제외

> **이번 3종은 모두 정상이었다.** 한글 깨짐 0%, 한글 비율 69~70%로 추출 품질이 좋았다.
> 인덱싱 전에 `inspect_parse.py`로 추출 텍스트를 눈으로 확인한 결과다.

```
134쪽 정제 결과: 1,114자 → 1,107자 (줄 끝 공백 정리)
문서 전체:  474,960자 → 462,120자 (목차 6쪽 제외)
```

### [3] 청킹 — 검색 단위로 자른다

문서 한 권을 통째로 벡터 하나로 만들면 "이 책은 금융에 관한 것" 수준의 뭉뚱그린 의미만 남는다.
반대로 너무 잘게 자르면 문맥이 끊긴다. 그래서 **800자 단위**로 자르되:

- **문단 경계를 우선**한다. 문단이 길면 문장 경계에서, 그래도 길면 강제로 자른다.
  → 문장 중간에서 끊겨 의미가 깨지는 걸 막는다.
- **앞 청크의 끝 150자를 다음 청크 앞에 겹쳐 넣는다(오버랩).**
  → 경계에 걸친 내용이 어느 쪽에서도 안 잡히는 일을 막는다.
- 100자 미만의 자투리 청크는 옆 청크에 합친다.

```
결과: 2,381개 청크 · 평균 641자 · 최소 163자 · 최대 802자
134쪽 → chunk_index 215번 (684자)
```

### [4] 임베딩 — 글을 숫자 벡터로 바꾼다

**BAAI/bge-m3** 모델로 각 청크를 **1024개의 숫자**로 변환한다.
이 모델은 한국어를 포함한 다국어로 학습돼 "빚내서 투자"와 "레버리지"가 비슷한 위치에 놓이게 만든다.
API 키가 필요 없는 로컬 모델이라 비용 없이 돌아간다(OpenAI로 바꾸는 설정도 열어뒀다).

```
chunk 215번 → [-0.0220153, 0.0283301, -0.0281541, 0.0274769, -0.0318157, ... ] (1024개)
```

벡터는 길이 1로 정규화해 저장한다. 그래야 두 벡터의 내적이 곧 **코사인 유사도**(-1~1, 클수록 유사)가 된다.

### [5] 적재 — PostgreSQL에 넣는다

pgvector 확장을 쓴 두 테이블에 저장한다.

```sql
edu_documents   -- 문서 1건 = 1행 (제목·기관·대상·연도·라이선스·파일해시)
edu_chunks      -- 청크 1건 = 1행 (본문·페이지범위·주제태그·embedding vector(1024))
```

실제 적재된 행:

```
id=8689  chunk_index=215  page_start=134  page_end=134  content길이=684
topic_tags={실용금융, 투자의기초, 신용의이해와관리, 대출, 금융사기예방, 레버리지}
embedding=[-0.0220153, 0.0283301, ...]  ← 1024차원
소속 문서='대학생을 위한 실용금융 (제4판)'   file_hash=6f8499f676b64e63...
```

인덱스 2종을 건다.
- **HNSW (코사인)** — 2,381개 벡터를 전부 비교하지 않고 가까운 것만 빠르게 찾는 근사 최근접 탐색용
- **GIN (topic_tags)** — "레버리지 태그가 붙은 것 중에서" 같은 필터를 빠르게 걸기 위함

**재실행 안전장치**: 파일 해시(SHA-256)를 저장해 두고, 내용이 그대로면 건너뛴다.
파일이 바뀌면 그 문서의 청크만 지우고 다시 넣는다. → 자료를 추가할 때 전체를 다시 돌릴 필요가 없다.

## 5. 그래서 어떻게 쓰이는가 (검색)

질문도 똑같이 벡터로 바꿔서, DB의 2,381개 벡터 중 **가장 가까운 것**을 찾는다.

```bash
python3 search.py "금융사기를 예방하는 방법" --top-k 5
python3 search.py "빚내서 투자하면 생기는 일" --tags 레버리지 --target U
```

실제 결과(유사도는 1에 가까울수록 유사):

| 질문 | 유사도 | 찾아온 근거 |
|---|---|---|
| 예금자보호 한도 | **0.77** | 금감원 실용금융 **115–116쪽** — 5천만원 초과 시 분산 예치 설명 |
| 금융사기를 예방하는 방법 | **0.76** | 예보 금융 첫걸음 **409–410쪽** — 사기 예방 금융습관 |
| 레버리지 투자의 위험성 | **0.73** | 금감원 실용금융 **134–135쪽** — 레버리지 효과·손실 확대 |
| 복리 효과란 (대학생 자료만) | **0.64** | 예보 금융 첫걸음 **90–91쪽** — 복리 이자 계산 |

주제 태그(`--tags`)·교육대상(`--target`) 필터가 벡터 유사도와 AND로 결합된다.
→ "레버리지 주제의, 대학생용 자료에서만" 같은 조건 검색이 가능하다.

**다음 단계인 챗봇은 여기서 찾아온 청크를 LLM에 근거로 넘겨 답변을 만들게 된다.**
(답변 생성은 이번 범위 밖)

## 6. 구축 과정에서 발견하고 해결한 문제

문서화 가치가 있는 것 세 가지. 모두 실측으로 확인하고 고쳤다.

### (1) Apple Silicon GPU에서 임베딩이 깨지는 문제 — 가장 치명적

맥의 GPU(mps)로 모델을 돌리면 **짧은 텍스트를 단독으로 인코딩할 때 벡터가 망가진다.**

| 디바이스 | 같은 질의의 단건 vs 배치 인코딩 일치도 | 질의·문서 유사도 |
|---|---|---|
| mps (GPU) | **0.2372** | **0.1175** |
| cpu | 1.0000 | 0.7156 |

검색은 구조상 항상 질의 하나만 인코딩하므로 **검색이 통째로 망가진다.**
인덱싱은 긴 텍스트를 묶어서 처리하기 때문에 영향이 없어서, **"적재된 데이터는 멀쩡한데 검색만 이상한"**
형태로 나타나 원인을 찾기 어려웠다. 저장 벡터와 재계산 벡터 일치도 1.0000, HNSW 결과와 순차탐색 결과 일치까지
확인한 뒤에야 모델 인코딩 단계로 좁혀졌다.

→ **조치**: 임베딩 디바이스를 CPU로 고정(`config.yaml`). 인덱싱이 3분→8분으로 늘었지만 검색이 정상화됐다.
→ **효과**: "금융사기를 예방하는 방법" 검색이 **0.22(목차 조각) → 0.76(예보 409쪽 정답)** 으로 개선.

### (2) 청크가 설정값을 초과

오버랩을 문단 단위로 가져오다 보니 마지막 문단이 길면 오버랩이 수백 자로 불어나,
800자 설정에 **1,225자 청크**가 생성됐다. 청크가 길수록 여러 주제가 섞여 검색 정확도가 떨어진다.
→ 글자 수 기준으로 자르도록 수정, **최대 802자**로 정상화.

### (3) 목차가 본문으로 섞여 들어감

목차의 점선(리더 문자)이 책마다 달랐다 — `......`, `・・・・・`, `⋯⋯⋯`.
금감원 자료는 `⋯`(U+22EF)를 써서 목차가 **한 쪽도 걸러지지 않았고**, 검색 상위에 목차 조각이 올라왔다.
→ 리더 문자군을 확장, 문서당 6~16쪽이 제외되도록 개선.

## 7. 한계와 다음 과제

| 한계 | 내용 | 대응 |
|---|---|---|
| **핵심 주제 자료 부족** | "반대매매"가 3종 자료 전체에서 6개 청크에만, 그것도 전부 선물·차익거래 문맥. **신용거래 담보부족에 따른 강제매도**를 설명하는 대목이 없음 | 트레이딩 짐의 핵심 시나리오이므로 신용거래·증거금·반대매매를 다루는 자료 추가 확보 필요 |
| **표 구조 유실** | 표가 셀 텍스트 나열로 풀려 행·열 대응이 사라짐 (예: "복리와 단리 비교" 표) | 내용은 남아 검색에는 걸림. 필요 시 표만 별도 추출해 마크다운으로 재구성 |
| **머리글 일부 잔존** | 좌·우 페이지가 다른 머리글을 쓰면 각각 43%씩 반복돼 제거 임계값(50%)에 미달 | 임계값을 30%로 낮추면 해결. 재인덱싱 필요 |
| **자동 수집 미연동** | 현재 메타데이터는 수기 CSV | Open API 승인 후 수집기의 `catalog.jsonl`을 두면 자동 병합되도록 이미 분리해둠 |

## 8. 재현 방법

```bash
cd edu-rag-indexer
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt

createdb trading_gym_rag
psql -d trading_gym_rag -c "CREATE EXTENSION vector;"

.venv/bin/python inspect_parse.py     # 파싱 품질 육안 확인
.venv/bin/python indexer.py           # 인덱싱 (약 9분)
.venv/bin/python search.py "레버리지 투자의 위험성"
```

접속 정보: `postgresql://hbrc@localhost:5432/trading_gym_rag` (로컬 trust 인증, 비밀번호 없음)

상세 사용법은 [README.md](README.md), 요구사항 명세는 [SPEC.md](SPEC.md) 참조.
