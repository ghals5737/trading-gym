# mock-exam — 모의고사 → 행동진단 → RAG 맞춤 퀴즈

모의고사를 풀게 하고, **왜 그렇게 판단했는지 적은 메모**를 분석해 행동 습관을 진단한 뒤,
`edu_chunks`(금융교육 자료 벡터 DB)에서 근거를 찾아 맞춤 퀴즈를 만드는 파이프라인.

대상 DB는 **로컬 `trading_gym_rag`** (RDS 아님).

```
모의고사 응시 ──▶ 진단 ──▶ RAG 검색 ──▶ 퀴즈 생성 ──▶ 저장
 (판단 + 메모)    (메모에서    (edu_chunks    (LLM/stub)   (근거 chunk_id
                  패턴 추출)    벡터 검색)                   함께 고정)
```

## 왜 메모가 핵심인가

매매 기록만 보면 "1턴에 매수했다"까지만 알 수 있다. 하지만 **왜 샀는지**를 모르면
같은 오답이라도 원인이 다른 걸 구분할 수 없다.

| 같은 "매수" 판단 | 메모 | 진단 | 찾아오는 자료 |
|---|---|---|---|
| 1턴 종목 A | "리딩방에서 마지막 기회라고 해서" | NEWS_CHASING | 정보 검증 없이 추천만 믿는 위험 |
| 3턴 종목 C | "평단가를 낮추려고" | LOSS_AVERSION | 손절 기준과 물타기의 위험 |
| 4턴 종목 D | "다들 사는 분위기라 그냥 느낌이" | HERD_FOLLOWING + NO_RATIONALE | 군중심리·테마주 과열 |

메모가 있어야 이 구분이 가능하고, 그래야 사람마다 다른 문제가 나온다.

## 실행

```bash

psql -d trading_gym_rag -f seed_attempt.sql  # 초보자 전형 응시 기록

# 1) 진단만 보기
```

## 테이블 구조

**문제지와 응시를 분리**했다. 같은 모의고사를 여러 명이 풀고, 재응시로 개선 여부를
봐야 하기 때문이다.

```
investor_profiles   투자성향 (온보딩 결과) — 응시의 컨텍스트

exam_papers         모의고사 1회분
  └ exam_turns      턴 = 문항. 차트·뉴스·공시를 JSONB로 자체 보유(시세 테이블 불필요)

exam_attempts       응시
  └ exam_responses  턴별 응답 + reason_memo(★) + viewed_disclosure
  └ exam_diagnoses  진단된 패턴 + evidence(근거 메모) + rag_query

quiz_sets           응시 1회 → 퀴즈 세트
  └ quiz_questions  문항 + source_chunk_id → edu_chunks(★ 근거 고정)
      └ quiz_options
      └ quiz_responses
```

설계상 눌러둔 지점 세 가지:

1. **턴이 자체 완결적이다.** 차트·뉴스·공시가 행 안에 JSONB로 있어 시세 테이블에
   의존하지 않는다. 모의고사는 큐레이션된 고정 문제라 실시간 시세가 필요 없고,
   API 장애·장 마감과 무관하게 데모가 된다.
2. **정답 영역이 분리돼 있다.** `outcome_*`·`ideal_*`은 응답 제출 후에만 노출한다.
   프론트에서 이 필드를 제출 전에 렌더하면 안 된다.
3. **`quiz_questions.source_chunk_id`가 `edu_chunks`를 직접 참조한다.** 문제마다
   "근거: 금감원 실용금융 159–160쪽"을 확정적으로 붙일 수 있어야 할루시네이션 방어가 된다.

## 진단 패턴

메모의 **표현 + 행동**으로 판정하는 규칙 기반이다. LLM도 RAG도 쓰지 않는다
(둘은 진단이 끝난 *다음* 단계에서 들어온다).

- 실제 서비스가 쓰는 정의: `backend/…/service/ExamDiagnosisRules.kt`
- 파이썬 프로토타입에도 같은 규칙이 있다: `quizgen.py`의 `PATTERNS`
  (배치 실행용. 규칙을 고치면 두 곳을 같이 고쳐야 한다)

| 패턴 | 감지 신호 | RAG 검색 질의 |
|---|---|---|
| `NEWS_CHASING` | 리딩방·추천·마지막 기회·실검 + 매수 | 정보를 검증하지 않고 추천만 믿고 매수하는 위험 |
| `HERD_FOLLOWING` | 다들·분위기·뒤처·인증 + 매수 | 군중심리와 과열된 테마주의 위험 |
| `PANIC_SELL` | 무서·불안·더 떨어질 + 매도 | 급락장에서 공포에 파는 심리와 대응 |
| `LOSS_AVERSION` | 평단·물타기·손실이 확정·버티 | 손절 기준 세우기와 물타기 회피 |
| `NO_RATIONALE` | 느낌·그냥·왠지 | 투자 판단 기준 세우기 |
| `DISCLOSURE_IGNORED` | 매수의 50%+ 에서 공시 미열람 | 재무제표·공시 확인 방법 |

### 패턴 하나

```kotlin
Pattern(
  "HERD_FOLLOWING",                    // 코드
  "남들 따라 사기(군중심리)",             // 화면에 보일 이름
  listOf("다들","남들","분위기","뒤처","인증","1위","너도나도"),  // ← 표현
  setOf(ExamAction.BUY),               // ← 행동
  "군중심리에 휩쓸린 투자와 과열된 테마주의 위험",  // 이 패턴으로 edu_chunks를 검색할 질의
)
```

"표현 + 행동"이란 **3번째와 4번째 줄을 둘 다 만족해야** 한다는 뜻이다.

### 판정 코드

```kotlin
val evidence = rows
    .filter { it.action in pattern.actions }                                 // ① 행동이 맞나
    .mapNotNull { row ->
        val matched = pattern.keywords.filter { row.reasonMemo.contains(it) }  // ② 표현이 있나
        if (matched.isEmpty()) null                                            //    없으면 탈락
        else Evidence(row.turnNo, …, matched, row.reasonMemo, …)               // ③ 근거로 남김
    }
```

`contains`는 문자열에 그 단어가 들어있는지만 본다 — 의미 분석이 아니라 Ctrl+F 수준이다.

### 실제 데이터로 따라가기

4턴 응답이 이랬다고 하자.

```
action = BUY
memo   = "실검 1위에 다들 사는 분위기라 그냥 느낌이 좋았어요"
```

**HERD_FOLLOWING을 통과시키면:**

| 검사 | 결과 |
|---|---|
| ① 행동이 `BUY`인가 | `BUY` ∈ `{BUY}` → 통과 |
| ② 키워드 7개 중 메모에 있는 것 | `다들` ✓ `분위기` ✓ `1위` ✓ (나머지 ✗) |
| ③ 결과 | `matched = ["다들","분위기","1위"]` → **진단됨** |

**PANIC_SELL은 같은 메모로 통과하지 못한다:**

| 검사 | 결과 |
|---|---|
| ① 행동이 `SELL`인가 | `BUY` ∉ `{SELL}` → 여기서 탈락 (메모는 보지도 않음) |

그래서 "무서워서 **샀어요**"는 '무서'가 들어 있어도 공포매도로 잡히지 않는다. 행동이 매수라서다.

### 왜 "항상 설명할 수 있다"인가

`matched`를 버리지 않고 `evidence`에 함께 저장하기 때문이다.

```json
{ "turnNo": 4,
  "matched": ["다들", "분위기", "1위"],
  "memo": "실검 1위에 다들 사는 분위기라 그냥 느낌이 좋았어요",
  "wasWrong": true }
```

이 값이 그대로 화면에 나간다.

```
[주의] 남들 따라 사기(군중심리)  3회
  4턴 종목 D · 매수 · 아쉬운 판단 · 감지: 다들, 분위기, 1위
  "실검 1위에 다들 사는 분위기라 그냥 느낌이 좋았어요"
```

LLM에게 진단을 맡겼다면 돌아오는 건 `"HERD_FOLLOWING"`이라는 라벨뿐이고, 왜 그렇게
봤는지는 모델 안에 있어 꺼낼 수 없다. "이 진단의 근거가 뭐냐"는 질문에
**"이 세 단어를 쓰셨기 때문"**이라고 화면으로 답할 수 있는 것이 규칙 기반의 값어치다.
같은 메모를 넣으면 항상 같은 결과가 나오므로 재도전 전후 비교도 성립한다.

### 이 방식의 한계 (실측)

미리 정한 단어를 쓴 사람만 진단된다. 뜻은 같고 표현만 다른 메모로 5턴을 넣어봤더니
진단이 **6개 → 2개**로 줄었다.

| 메모 (의도) | 결과 |
|---|---|
| "**친구들이 죄다** 이거 샀다고 해서 저도 **따라** 들어갔어요" (군중심리) | 못 잡음 |
| "**손해 보고 팔기 싫어서** 조금 더 사서 **단가를 내렸어요**" (물타기) | 못 잡음 |
| "**화제가 되길래 별 생각 없이** 올라탔습니다" (추격매수) | 못 잡음 |
| "**겁**이 나서라기보다 손실이 커질까 싶어 정리했습니다" | '겁'이 우연히 걸림 |

목업 시나리오는 키워드가 들어가도록 설계돼 있어 잘 동작하지만, 실제 사용자가 자기 말로
쓰면 상당수를 놓친다. 개선 방향은 세 가지다.

| 방법 | 장점 | 단점 |
|---|---|---|
| 키워드 확장 | 구조 그대로, 비용 0 | 표현은 무한해서 여전히 놓침 |
| LLM 분류로 교체 | 표현이 달라도 의도를 잡음 | 설명 가능성·재현성을 잃음 |
| **하이브리드** | 규칙이 먼저 잡고, 못 잡은 메모만 LLM에 넘김 | 구현이 조금 복잡 |

하이브리드로 가면 규칙이 잡은 건 "감지: 다들, 분위기"로 근거를 보여주고 LLM이 잡은 건
"AI 판단"으로 구분 표시할 수 있어, 설명 가능성을 지키면서 놓침을 줄일 수 있다.

### 심각도와 출제 개수

심각도는 **틀린 판단 수**로 매긴다 — 2회 이상 `HIGH`, 1회 `MEDIUM`, 0회 `LOW`.
맞은 판단에서 표현이 잡히면 근거에는 남지만 심각도를 올리지는 않는다.

패턴이 여러 개면 **심각도 → 빈도** 순으로 정렬해 상위 3개만 문제로 만든다
(백엔드는 `maxQuestions`, 파이썬은 `--max-questions`). 다 내면 학습이 아니라 시험이 되고
LLM 호출 비용도 늘어난다.

## 목업 데이터

`seed.sql`의 5턴은 각각 다른 실수를 유도하도록 짰다. 종목명은 전부 익명 처리했다.

| 턴 | 상황 | 모범답안 | 결과 | 유도하는 실수 |
|---|---|---|---|---|
| 1 | 급등주 + 리딩방 "마지막 기회" (공시엔 적자·CB) | HOLD | -42% | 추격매수 |
| 2 | 급락장 우량주 (공시는 무차입·실적개선) | HOLD | +72% | 공포매도 |
| 3 | 보유종목 -18% + "평단 낮추세요" | SELL | -45% | 물타기 |
| 4 | 테마주 3주 +155% + 실검 1위 | HOLD | -63% | 군중심리 |
| 5 | 조용한 실적개선주 (분위기 최악) | BUY | +36% | 공시를 봐야 정답 |

`seed_attempt.sql`은 "리딩방 의존 초보자"가 5턴 중 4턴을 틀리는 응시 기록이다.
실행하면 진단 6개가 잡히고 퀴즈 3문항이 생성된다.

## 프론트 연동

`export_mock.py`가 `mock-data.json`을 만든다. 백엔드 API가 붙기 전까지 프론트는 이
파일을 import해서 화면을 만들면 되고, API가 생기면 같은 모양의 응답으로 갈아끼우면 된다
(그래서 필드명을 API 응답 가정으로 camelCase로 맞춰뒀다).

```jsonc
{
  "profile":  { "riskType": "AGGRESSIVE", "infoHabit": "DEPENDENT", ... },
  "paper":    { "title": "첫 모의고사 · 판단의 근거 찾기", "totalTurns": 5, ... },
  "turns":    [ { "turnNo": 1, "chartPoints": [...], "news": [...],
                  "disclosure": {...},          // '공시 보기' 눌렀을 때만 노출
                  "outcome": {...} } ],          // 제출 후에만 노출
  "attempt":  { "responses": [ { "action": "BUY", "reasonMemo": "...", ... } ] },
  "diagnoses":[ { "patternKey": "HERD_FOLLOWING", "severity": "HIGH", "evidence": [...] } ],
  "quizSet":  { "headline": "...", "questions": [ { "source": { "title", "pageStart" }, ... } ] }
}
```

### 화면 흐름 제안

```
[모의고사 진행]  차트 + 뉴스 3건 ─┬─ [공시 보기] (열람 여부를 기록 → 진단에 사용)
                                 └─ 매수 / 매도 / 관망 선택
                                    + 메모칸 "왜 그렇게 판단했나요?" (필수, 20자 이상 권장)
                                    ↓ 제출
[결과 공개]      이후 실제 주가 흐름 + 모범답안 + 학습 포인트
                                    ↓ 5턴 반복
[진단 리포트]    "남들 따라 사기 습관이 3번 보였어요" + 근거가 된 내 메모 인용
                                    ↓
[맞춤 퀴즈]      3문항 + 각 문항에 "왜 이 문제인지" + 근거 자료 쪽수
```

메모칸은 **필수**로 두는 게 좋다. 이게 없으면 진단이 행동 통계 수준으로 떨어지고,
"내 메모를 읽고 만든 문제"라는 이 서비스의 차별점이 사라진다.

## 현재 검증된 결과

목업 응시(5턴 중 4턴 오답, 공시 1회 열람) 기준:

- 진단 6개 — HERD_FOLLOWING/DISCLOSURE_IGNORED/NEWS_CHASING(HIGH), PANIC_SELL/LOSS_AVERSION/NO_RATIONALE(MEDIUM)
- 퀴즈 3문항, 각각 다른 턴을 인용(4턴·3턴·1턴)하고 근거 자료가 붙음
  - 공시 확인 문제 → 금감원 실용금융 159–160쪽 (유사도 0.696)
  - 추격매수 문제 → 금감원 실용금융 169–170쪽 (유사도 0.588)
  - 군중심리 문제 → 금감원 실용금융 543–544쪽 (유사도 0.551)

## LLM 생성기 선택

`LLM_PROVIDER`(openai | anthropic | stub)와 키 유무로 자동 결정된다. 키는 저장소 루트
`.env`에서 읽는다(`.env`는 gitignore 대상 — 절대 커밋 금지).

```bash
# .env
OPENAI_API_KEY=sk-...
# OPENAI_MODEL=gpt-4.1-nano   # 더 싸게 가려면
```

키가 없으면 stub으로 떨어져 **키 없이도 데모는 항상 동작**한다.

### 모델 비교 (실측)

같은 응시 데이터로 세 생성기를 돌려봤다. 응시 1회 = 3문항 = 입력 5,229 + 출력 640~816 토큰.

| 모델 | 응시 1회 비용 | 1,000회 | 품질 |
|---|---|---|---|
| `gpt-4o-mini` **(기본값)** | 약 1.6원 | 약 1,600원 | 문제·보기가 자연스럽고, 사용자 메모를 직접 인용 |
| `gpt-4.1-nano` | 약 1.2원 | 약 1,200원 | **정답이 2개 성립하는 문제 발생**, 조어("밀실적 판단 능력"), 메모 인용 지시 무시 |
| `stub` | 0원 | 0원 | 패턴별 고정 문항. 근거 연결·저장 경로는 동일하게 동작 |

nano가 최저가지만 차이가 1,000회에 440원 수준이라 기본값은 `gpt-4o-mini`로 뒀다.
정답이 두 개인 문제는 문제로 성립하지 않아, 그 리스크를 400원에 사는 셈이기 때문이다.
(단가는 공식 가격표 기준 추정치이므로 실제 청구액은 대시보드에서 확인할 것)

프롬프트에는 "정답은 하나만 성립할 것", "사용자 메모를 직접 인용할 것", "조어 금지"를
명시했고, 생성된 JSON은 `validate()`가 검사해 형식이 깨지면 stub으로 자동 폴백한다.

## 남은 것

- **자료 편중** — 3문항 모두 금감원 실용금융에서 나왔다. 자료가 3종뿐이라 그렇고,
  특히 군중심리 쪽은 유사도 0.55로 낮은 편이다. 자료를 늘리면 개선된다.
- **생성 품질 자동 검증 없음** — `validate()`는 형식(보기 4개, 정답 인덱스 범위)만 본다.
  "정답이 두 개 성립하는가" 같은 내용 검증은 사람이 봐야 한다. 문항을 대량 생성할 계획이면
  검수 화면이나 2차 LLM 검증이 필요하다.
- **백엔드 이식** — 지금은 파이썬 CLI다. Kotlin 백엔드에 붙일 때 진단 로직(규칙)은
  그대로 옮기고, 벡터 검색만 `edu-rag-indexer/web_search.py`의 `/api/search`를 호출하면 된다.
